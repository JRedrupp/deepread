# Tech Debt

Known limitations of the MVP architecture. These are accepted trade-offs to ship an MVP quickly, not bugs with a one-time fix — several are ongoing tuning work.

- **Rendering heuristic is imperfect.** The renderer waits for `networkidle` with a timeout fallback to `domcontentloaded` + a fixed wait. This will misrender some sites (infinite scroll, lazy-loaded content, aggressive anti-bot measures). Expect this to need ongoing per-site tuning, not a single fix.
- **No dedicated job queue.** The `articles.status` column (`pending`/`rendering`/`ready`/`failed`) acts as an implicit queue inside a single worker process. This works at MVP scale but won't scale or recover from crashes as gracefully as a real queue (e.g. Redis) would.
- **No dead-letter/admin visibility.** Failed renders only have `retry_count` and `status='failed'` — there's no UI or alerting to see what's failing or why.
- **On-device storage growth is unbounded by default.** `RetentionService` (auto-expire read articles after N days, cap articles kept per feed, both run from `syncNow` on every sync) and a manual "Clear downloaded articles" action now exist in Settings — but `SettingsRepository.retentionExpireReadAfterDays`/`retentionCapPerFeed` both default to `null` (off), intentionally, for upgrade safety. A user who never opens Settings still accumulates downloaded HTML + images without bound; the mechanism exists, the default behavior doesn't use it.
- **No per-user quotas or rate limiting.** Being a public app with essentially no cost-abuse protection beyond basic sanity limits is a real cost risk if usage grows unexpectedly.
- **Read/unread state is local-only.** It's stored in the client's local SQLite (`drift`) DB and does not sync across a user's own devices — it will diverge.
- **Copyright/legal exposure is mitigated, not eliminated.** The shared rendering cache stores and serves full-text article copies to arbitrary public users. Paywall avoidance, robots.txt respect, and a takedown-request flow reduce risk, but no formal legal review has been done — see the blocking items in TODO.md before any real public launch.
- **Takedown requests have no review tooling.** Filing one (in-app "Report content issue") writes a row to `takedown_requests` — there's no admin UI, no email alert, no SLA. Whoever operates the backend has to query the table manually.
- **Stuck `rendering` rows: reclaimed, but latency and fencing are accepted trade-offs.** The renderer claims a `pending` article by flipping it to `status='rendering'` and stamping `claimed_at` (an optimistic lock so two worker replicas can't render the same article twice — see `deepread_worker.renderer._render_one`). `deepread_worker.cleanup`'s `run_cleanup_pass` runs an unconditional fourth phase (`list_stale_claims`/`reclaim_stale_claims`) that resets any `rendering` row whose `claimed_at` is older than `stale_claim_minutes` (default 30min, or already null) back to `pending`, or to `failed` once `retry_count` has hit `render_max_retries` — recovering both a crashed worker's abandoned claim and a transient render failure that never made it to `_mark_retry_or_failed`. Two things remain worth naming as accepted trade-offs rather than fixed:
  - **Reclaim latency is bounded by `cleanup_interval_seconds` (default 6h), not `stale_claim_minutes`.** The sweep only runs once per cleanup pass, so a claim that goes stale at the 30-minute mark can sit unreclaimed until the next pass — up to ~6.5h for a single crashed article, and up to ~18h (three passes, each bumping `retry_count`) for a URL that reliably crashes the renderer to converge to `status='failed'`. Nothing else is blocked in the meantime, so this isn't a defect, but 30 minutes is not the real recovery bound in practice.
  - **The claim is not a true fence.** `_render_one`'s terminal updates (the `ready`/`failed` writes, and `_mark_retry_or_failed` in `renderer.py`) update by row `id` only, with no `.eq("status", "rendering")` guard. If a render is still running past `stale_claim_minutes` when the sweep reclaims its row, the render's own late write can land after the reclaim and clobber it — e.g. resurrecting a sweep-marked `failed` row back to `pending`/`ready` with a stale `retry_count`. This needs an in-flight render exceeding 30 minutes to trigger (nav timeout alone is ~15s), so it's low-severity, but it's a genuine gap, not a closed one.
- **Testing constraint: drift's `.watch()` stream doesn't reliably fire inside a `testWidgets` fake-async zone.** Subscribing to a live drift query stream (directly, or via a `StreamBuilder` built during `pumpWidget`) inside a `testWidgets` body hangs indefinitely — confirmed via multiple isolated repros, including with `tester.runAsync` wrapping. It works fine in a plain `test()` body, or via `tester.runAsync` around a direct `await stream.first`. The workaround used throughout `mobile/`: widgets that consume a drift stream (e.g. `FeedListScreen`) take an injectable `Stream` parameter defaulting to the live query, so widget tests can pass `Stream.value(...)` instead of touching drift at all. Follow that pattern for any new screen backed by a `.watch()` query — don't re-debug this.
- **No billing/monetization infrastructure exists.** The business model itself is undecided (see TODO.md); nothing here should be assumed as a default.
- **`riverpod` is an unused dependency.** It's in `pubspec.yaml` for planned app-wide state management, but the app currently uses plain `StatefulWidget`/`setState` throughout and works fine that way. Either adopt it when state genuinely gets complex enough to need it, or drop the dependency — don't add it just to justify the import.
- **GitHub Actions cache usage is already near/over the repo's 10GB eviction cap** (measured ~12.6GB across 39 active entries via `gh api /repos/JRedrupp/deepread/actions/cache/usage`, checked 2026-08-03 — up from ~10.8GB/24 entries). Each PR's `mobile-test`/`backend-test` run creates its own PR-scoped caches (Flutter SDK, pub packages, `.dart_tool`, Playwright Chromium, pip); these are naturally pruned once a PR closes and its cache goes unused for 7 days, but ongoing PR churn keeps total usage high in the meantime. This matters for `ci.yml`'s `develop`-scoped cache-warming caches (see `CLAUDE.md`'s CI section) — if total usage stays pinned at/over the cap, GitHub's LRU eviction could reclaim even the `develop` caches between accesses, silently reintroducing cold-start CI runs. Not fixed here; if it recurs, look at trimming what's cached (e.g. the Playwright browser download is likely the largest single entry) rather than disabling cache-warming.
- **Local-data wipe on sign-out is best-effort, not guaranteed.** The wipe (`resetLocalData` in `mobile/lib/features/auth/local_data_reset.dart`) runs from `_signOut`, a handler defined in `HomeShell` and passed down to the "Sign out" tile on the Settings screen — not as a reaction to the `signedOut` auth state itself — so a session-expiry-triggered sign-out, or the app being killed mid-wipe, leaves stale data for the next user to sign into. There's also a narrow race with the periodic background sync isolate: a `WorkManager` task already past its `currentUser`-null check at the moment of sign-out can still write under the outgoing user's identity before the wipe runs. A durable fix (out of scope here) would persist the last-signed-in user id and compare it against `currentUser.id` on the next `signedIn` event in `AuthGate`, wiping there if it changed — a reaction to auth state, not a specific button.
- **iOS background sync is wired up but unverified on real hardware.** `BGTaskSchedulerPermittedIdentifiers`/`UIBackgroundModes` (`mobile/ios/Runner/Info.plist`), the `WorkmanagerPlugin.registerPeriodicTask(withIdentifier:frequency:)` call (`mobile/ios/Runner/AppDelegate.swift`), the iOS deployment target bump from 13.0 to 14.0, and the new `mobile/ios/Podfile` were added by reading the `workmanager_apple` plugin's source directly, in a dev environment with no macOS/Xcode/iPhone available to build or run it. `.github/workflows/ci.yml`'s `mobile-ios-compile-check` job (macOS runner) confirms it compiles, but `BGTaskScheduler`'s actual background-execution behavior — whether the task fires, how often, under what OS conditions — has never been observed on a real device or simulator. Treat as unconfirmed until someone with Mac/iPhone access checks it. There's also a real, if minor, product-behavior gap worth tracking here: Android honors the user's chosen sync frequency (the Settings screen's 15/30/60/180-minute presets), but iOS's reschedule interval is currently hardcoded to the `workmanager_apple` plugin's 15-minute default (`AppDelegate.swift` passes `frequency: nil`) regardless of what the user picks in Settings.
